**定位与修复**

| 问题 | 实际复现与处理 |
| --- | --- |
| 集成测试无法编译 | 同一函数已有 int64 的 `before`，解码游标又向它赋 `*time.Time`。改名为 `beforeTime` 后，带 integration 标签的 vet 和测试通过 |
| 正常领取误加失败次数 | MySQL 单表 UPDATE 先将 status 写成 running，后续表达式读取到新值。正常 pending 任务出现内存失败数 0、数据库失败数 1。调整赋值顺序，添加真实数据库断言 |
| 成功批次未清零内存失败数 | 批次提交把数据库计数清零，但当前任务对象仍保留旧值，会影响后续退避和失败判定。提交成功后同步清零，并验证历史失败后的成功批次 |
| Redis context 未控制 IO | 已取消的调用仍建立索引；20 ms 预算实际等待约 524 ms。新投影操作使用独占连接、context 拨号与取消时关闭连接，保持现有投票/Session 连接池独立。复测约 20 ms 返回；取消前已失效的调用不写入 |
| 正常处理预算被计为失败 | 扇出任务预算耗尽且批次 SQL 因此取消时，被设置为 retry 并增加失败数 1。改为正常让出；相同定向检查得到 pending、连续失败数 0 |

另外修正运行说明中显式 `-f` 与默认 override 的区别，并在 MySQL 定向测试前要求停止同一专用库上的应用 Worker，避免测试竞争同一任务队列。

新投影 Redis 操作每次建立独占连接，以实现真实取消且不关闭其他请求使用的连接。该选择有连接建立成本，本轮没有量化其吞吐影响。Redis 写超时的执行结果仍可能未知，依靠保留任务和幂等投影恢复。

**真实 API 与状态核对**

- 通过注册、登录和关注 API 创建作者、三位粉丝与无关注用户。发布六篇内容后，MySQL 同时存在六个事件及十二项 pending 任务；详情可读，索引未建立时投票返回 1014。
- 在十二项任务仍为 pending 时停止并重启应用。两类任务继续完成，每批两位粉丝，共生成十八个唯一引用。
- 推模式连续分页读出六篇内容，ID 为字符串；默认拉模式次序一致。未关注用户得到空列表，未登录用户被拒绝，跨用户及跨模式游标返回参数错误。
- 对已投票内容重新运行 index/fanout 任务，热度与票态版本保持，收件箱仍每位粉丝一条引用。赞成、重复赞成、改为反对、撤销后，MySQL 最终方向为 0、版本为 3。
- 独立索引任务失败时，fanout 仍完成并可从 push 读取。修正测试依赖后 index 重试完成。
- 取关后旧引用被即时过滤，重新关注后可读已有引用；`status=0` 的内容被过滤。最终七篇内容、三位粉丝，共二十一个收件箱引用，index/fanout 各七项 done。
- 真实缺失索引且无内容任务解释时，启动以非零退出码拒绝；rebuilding 标记同样拒绝。移除专用异常样本或恢复测试标记后，健康数据可启动。
- 新内容链路的真实 HTTP 指标包含任务结果与二十一个分发引用。执行计划样本使用 `idx_followee` 和 `idx_inbox_feed`；小样本不用于宣称性能收益。
