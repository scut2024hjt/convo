## 2. 本轮取舍

**新最新流用 MySQL 复合索引产生有序候选 ID，以 `(create_time DESC, post_id DESC)` 做 keyset 翻页。** 不用 Redis ZSET 的排名或同分成员字典序冒充数值 ID 次序，不走深 OFFSET。MySQL 已提交的可见内容可出现在新最新流；Redis 发布索引尚未就绪时，点赞人数可回退已持久化查询，不把内容发布成功解释为各投影已同步完成。

形成一个批量装配入口供新最新流、旧 `/posts2` 以及基础 `/posts` 使用，后续热榜可传入自己的有序 ID。它不自己决定排序、不暗中分页，也不加载当前用户私有状态。保留已有详情缓存；本轮不实现列表缓存、singleflight、可靠编辑失效、熔断或通用降级平台。

新增必要的 SQL 超时、批量大小与扫描预算，保证本轮读取有界。T06 再统一完善热点缓存、并发回源保护和失效补偿。

## 3. API 契约

新增匿名可访问的 `GET /api/v1/posts/latest`，沿用 HTTP/业务码信封。即便浏览器带 JWT，它也只返回公开字段，不附带个人点赞状态。

| 参数 | 契约 |
| --- | --- |
| `community_id` | 省略或规范字符串 `0` 表示全站；正 int64 十进制字符串表示单分类。负数、小数、溢出、非规范 ID 拒绝；不存在的正分类返回参数错误 |
| `limit` | 默认 20，允许 1—50；非法值拒绝，不静默取无限或负数 |
| `cursor` | 首次省略；后续使用原样不透明字符串，绑定分类与排序上下文，有长度上限 |

新路由排序固定为最新，不接受切换到热度。关键参数重复出现、游标与分类不符、旧 Feed 游标、未知版本/用途、超长/损坏/篡改游标都返回明确参数错误。不能在错误游标时静默回第一页。

成功 `data` 结构：

```json
{
  "items": [
    {
      "id": "9007199254740993",
      "author_id_str": "9007199254740995",
      "author_name": "author",
      "title": "title",
      "create_time": "2026-11-09T08:00:00Z",
      "vote_num": 3,
      "community": {"id": "1", "name": "分类名称"}
    }
  ],
  "next_cursor": "opaque-or-null",
  "has_more": true,
  "vote_count_freshness": "realtime"
}
```

实际无后续位置时 next_cursor 为 JSON null、has_more=false；空 items 必须是数组。公开 ID 字段使用十进制字符串，不能经 float64/JavaScript number 中转。新增接口可用卡片专用 DTO，旧接口的已有字段类型不整体改变。新增分类复用 community，不建立标签/画像系统。

`vote_count_freshness` 为 realtime 或 persisted；若该页任何计数用了 MySQL 回退，整页标为 persisted。它只描述计数来源的时效，不能暗示整页内容、多个批次或点赞数是同一事务快照。

## 4. 游标与一致性

1. 时间来自 MySQL `post.create_time`，按当前 TIMESTAMP(0) 的秒精度和数值 post_id 组合比较。统一真实 Unix 秒边界与 UTC 序列化，使用参数化 SQL，不能以 ID 或请求时间替换实际发布时间。MySQL 会话时区与驱动 loc 必须一致；仅对错读的 time.Time 调用 UTC() 不能修复偏移。补一组非 UTC 配置或等价的时区往返验证，避免相邻页错过同秒内容。
2. 首次查询记录固定上界 `(anchor_time, anchor_id)`；后续同时满足不高于上界、严格小于继续位置。游标携带版本、用途 latest、分类、固定上界、继续位置和到期时间。第一屏空源则直接结束。
3. 使用命名空间隔离的 HMAC-SHA256 签名及严格解码，密钥复用现有配置秘密并做用途隔离，不引入新平台。负载与签名 Base64URL，验证签名、长度、字段、ID/时间范围和位置关系。最大 token 2048 字符；到期默认 30 分钟，沿整条翻页链保持首次过期时间，不每页续命。
4. 最新列表是公开列表，游标不绑定用户，可跨匿名/登录会话继续。分类及用途必须绑定，不能挪到另一分类、热榜或关注流使用。limit 可在 1—50 内改变。
5. 过期与参数错误可复用现有 CodeInvalidParam，但文案/原因应能让页面提示刷新，不能当成网络错误无限重试同一游标。禁止修改既有业务码的数值顺序。
6. 不使用跨请求数据库事务，也不宣称 MVCC 快照。上界之后发布的较新内容留给刷新；迟提交但排序位置较旧的事务仍可能在后续页出现，已经越过的位置也可能漏过这种迟提交记录。删除与元数据可见性按本次读取生效。业务分页顺序固定不等于提交时间顺序或全局快照。
7. 旧 pull/push Feed 游标和消息版本不改变；不把现有未签名 Feed 游标直接当成新 latest 游标。

存量 NULL/零时间等无法排序的异常记录不伪造时间、不进入新最新流；迁移预检与说明中列出其数量和处理边界。正常内容的时间不因重建或分页被改写。详情仍遵守原有按 ID 可见性规则。

## 5. 有界过滤、补取与 has_more

候选 ID 查询只依赖 post 的可见性、分类和时间/ID索引，不逐条查询作者等信息。取候选后，批量装配再次核对当前可见性；候选与装配之间提交删除的内容也应被过滤。缺内容、缺作者/分类、不可排序等条目不能造成计数错位。

本轮默认每批候选最多 100 个、每页累计读取最多 500 个，页面最多输出 limit 项；所有循环共享整个请求的超时预算。可以设置更低边界用于测试，硬上限不允许被客户端放大。候选数、装配输入与请求次数都要有界，不能“直到凑满”为止无限查。

需要实现并测试以下位置规则：

- 为判断更多可展示内容，可找一条额外合法项；它不能被算作已经消费的内容。若已找到合法 lookahead，继续游标至少保证该合法项在下一页仍可读取，不能直接用整批最后一条候选生成游标而跳过它。
- 未找到额外合法项且预算耗尽时，允许短页甚至空页；继续位置推进到已检查的最后候选，has_more=true。这里表示仍有可继续的位置，不保证下一页必有可展示条目。
- 已证实源耗尽才返回 null/false。恰好到预算或批次边界而未证实耗尽，可保守多给一次继续请求。
- 非空继续游标必须严格推进；同一输入不能反复返回同一游标或同一段已消费条目。恢复缺失元数据不承诺把已越过的条目补回旧翻页链，刷新可重新读取。
- 后端查询失败不是“该条不存在”，不能吞异常、推进游标并返回伪成功空页。返回忙碌，客户端保留原游标重试。

必须覆盖“前面若干条过滤后补满”“中间条目缺失”“整段超过预算都不可展示”“恰好页长/源末尾”“lookahead 在下一批”等情况。技术预算只写日志/指标，页面不展示数据库扫描细节。

## 6. 通用批量装配

1. 入口接收有序 ID（单批最多 100），批量读可见内容，按去重后的作者/分类集合查询元数据，再按 ID 恢复输入顺序。可复用现有批量函数或采用等价批量 JOIN，但不能隐藏逐条请求。空输入不执行 SQL/Redis。
2. 点赞数以 post_id 为键关联，不按过滤前后的数组下标拼接；相同 ID 按首次出现顺序去重。SQL IN 的返回顺序不可信，不再依赖 FIND_IN_SET 维持应用顺序。
3. 点赞数走有界 Redis Pipeline/批量脚本；检查必要 ready 标记与键状态。计数不是净票数，始终只计 direction=1。发布索引未完成、Redis 不可读或键损坏时，可对本批一次 MySQL GROUP BY 回退，标记 persisted。不能把失败当 0，也不能逐条 CountPostUpVotes 回源。
4. 已有合法索引而某帖没有点赞成员，正常人数可以是 0。公共计数回退不能改写 Redis、发布 ready 或变更票态；本人状态继续使用 T03 自己的认证和语义门禁。
5. 所有 DAO 使用调用方 context；HTTP 请求取消向下传播。选定一个总预算（建议 3 秒）并与批次数上限一起生效，不在循环中不断重新给完整超时。DAO 不能用后台 context 延长整个请求。
6. 元数据不全可以过滤并记录有限原因；数据库/Redis 命令执行失败须按明确回退或错误处理，不能悄悄把所有异常转为“没有数据”。SQL 回退也失败时整个请求忙碌。
7. 新 latest 与旧 `/posts2`、基础 `/posts` 接入该批量入口，至少消除 `/posts` 的作者/分类逐条查询。旧响应字段与参数兼容；旧分页不在本轮宣称已升级为稳定 keyset。给旧入口添加合理参数上限，防负数/乘法溢出，不重写其排序产品契约。
8. 关注流当前已用 JOIN 查询、返回轻量模型，无需为形式统一增加额外计数或强制改写。T05 热榜应可直接复用新装配入口，不能复制第三套组装逻辑。

T04 可以仍然批量读 MySQL 内容；批量内容缓存、热点请求合并、TTL/失效补偿和回源并发闸门属于 T06。本轮不要把延迟双删重命名后宣称已解决可靠失效。

## 7. SQL 与迁移

新增顺序迁移 `006_latest_list_indexes.sql` 并同步 init.sql，预期至少覆盖全站 `(status, create_time, post_id)` 和分类 `(community_id, status, create_time, post_id)`。索引是否使用 DESC 可结合 MySQL 8 实测决定，不能只凭列名推断执行计划。保留现有发布、回填和 inbox 索引。

迁移只增加所需索引/必要模型约束，保留内容、关注代次、票态、消费去重及任务进度。不删除/重建业务表，不把 init.sql 用于旧库升级，不改变 005 已完成语义。给出 DDL 自动提交、重复索引/部分执行后的检查与恢复方式。

查询不做全表 COUNT 来支持 total，也不把所有 ID 拉入内存后排序。保留参数化 keyset SQL与 EXPLAIN（可选 ANALYZE）证据：全站/分类、首屏/中间/较深游标，说明实际索引、扫描和排序情况；不要仅 FORCE INDEX 后声称优化成功。

## 8. React 与必要观测

- 发现“最新”入口接新 API，提供全部/单分类切换、手动加载更多、刷新、结束和失败重试状态。用现有 community 数据；新 UI 称“分类”，不做全仓重命名。
- 分类、排序入口、登录状态或刷新代次改变时隔离旧请求；不能把迟到旧分类页追加到新列表。追加失败保留已加载内容与原继续游标；重复点击不并发重复追加。
- 空页但有继续游标时允许继续加载，不能误报“没有更多”或自动无限请求。过期/非法游标提供刷新入口。客户端去重属于保护，不能掩盖服务端游标一直不推进。
- 卡片展示点赞人数；计数回退时可提示“点赞人数可能有延迟”，不向产品页面展示 SQL、Redis、扫描预算或 mode 等实现术语。详情点赞、关注、本人删除和发帖回跳保持。
- 热度页保留旧入口，分类热榜与固定批次安排到 T05；本轮不能把旧动态分数列表包装成已完成的新热榜。默认 Feed 不改。
- 复用 HTTP 延迟/业务码指标；新增必要候选读取、过滤、预算耗尽和计数回退指标/日志，label 只用固定枚举，不带 post_id/user_id/community_id/cursor。ID/批次和扫描数可记录结构化日志，禁止凭据。
- 更新实际 Swagger 三份文件与调用样例，不只补注释。现有 Vite/React 锁文件原则上保持。
