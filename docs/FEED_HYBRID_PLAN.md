# Convo 关注 Feed 的推拉演进安排

更新日期：2026-11-08。本文由代码开发会话维护。结合用户“通过项目学习完整工程实践”的目标，混合 Feed 保留为后续进阶任务 T02B，具体插入顺序在 T02 验收后确定。用户随后澄清“工业界既用 push 也用 pull”不等于单条 Feed 必须混合；本文不再将 T02B 必须紧随 T02 或默认切换 hybrid 作为已确定前提。本文件是设计与学习安排，不是已实现说明，也不把未测出的性能收益写成结论。

**1. 当前实现与最终目标**

当前 T01 的两条读取路径互相独立：

| 入口 | 读取来源 | 当前边界 |
| --- | --- | --- |
| 默认或 `mode=pull` | 当前关注关系 JOIN 活跃帖子 | 可读历史内容；保留为兼容与对照路径 |
| `mode=push` | 本人 MySQL 收件箱，JOIN 当前关系及活跃帖子 | T01 只扇出新发布内容；历史补齐与关系代次在 T02 完成 |

这还不是混合 Feed。T02B 的设计目标是由服务端合并普通作者的收件箱引用与需要拉取的内容；普通用户无需选择技术模式。T02 可独立交付，不依赖混合方案完成。

这里的 push 指写时扇出到站内收件箱，pull 指读取时聚合。它们与 WebSocket、移动端消息推送不是同一概念。

**2. 为什么安排混合方案**

推模式把读取工作提前到发布之后：单帖需要的收件箱写入量随粉丝数增长。拉模式减少预先分发的写入与空间，但读请求要聚合关注内容。粉丝分布、发帖频率、读者活跃度、关注数量及保留范围共同决定成本，不能用一个粉丝数代表全部条件。

普通作者采用推、高扇出作者采用拉，是适合本项目继续深入的具体方案。推拉混合不是所有生产项目的统一标准，纯推也并非错误。我们的安排由学习目标与要掌握的场景决定；测量用于解释代价、选择参数和验证效果，不作为取消混合实现的理由。

可读资料与开源代码：

- 《Designing Data-Intensive Applications》第一章“Describing Load”的 Twitter 案例讨论普通作者扇出、高粉作者读时合并。这是历史架构案例，不能据此描述今天 X 的完整生产实现：[出版方试读](https://api.pageplace.de/preview/DT0400.9781491903117_A29629813/preview-9781491903117_A29629813.pdf)。
- Mastodon 的 [FanOutOnWriteService](https://github.com/mastodon/mastodon/blob/main/app/services/fan_out_on_write_service.rb)、[FeedInsertWorker](https://github.com/mastodon/mastodon/blob/main/app/workers/feed_insert_worker.rb) 可用于学习分批分发与可见性过滤。
- Mastodon 的 [FeedManager](https://github.com/mastodon/mastodon/blob/main/app/lib/feed_manager.rb)、[FollowService](https://github.com/mastodon/mastodon/blob/main/app/services/follow_service.rb) 可用于学习关注后合并历史及取关移除等业务边界。其窗口、存储与联邦逻辑不直接照搬。

**3. 开发次序**

| 任务 | 交付目标 | 默认读取安排 |
| --- | --- | --- |
| T01，已开发验收 | 可靠发布、独立索引与分批扇出、显式推模式 | 保持 pull |
| T02，下一轮 | 新关注补历史、关注代次、取关清理、本人删除及存量补齐 | 保持 pull；push 完成独立验收 |
| T02B，T02 后确定具体排期 | 分流、读时合并、去重、统一游标及策略切换覆盖 | 该任务明确默认入口升级，不提前承诺切换 |
| T03—T06 | 点赞兼容、发现分页、热榜与缓存保护 | 衔接已稳定的 Feed 接口 |

T02B 的详细任务书和插入顺序在 T02 验收后基于实际模型与学习优先级确定，不预设必须先于 T03—T06。本轮只把 T02 交给网页端，避免同时实现生命周期与分流导致输入和验收边界失控。T02 不抢先把 push 设成默认，也不要求先完成全面压测教学。

**4. T02B 必须解决的具体问题**

1. **作者分流。** 提供可配置规则及开发验证用的作者覆盖配置。首版可依据粉丝数估计单帖扇出成本，并记录规则局限。阈值是实验参数，不宣传为行业统一值；规则若自动变化，应有明确的采样、更新和防抖安排。
2. **持久化分发决定。** 发布事务保存该内容使用的分发策略或等价的可恢复边界；异步重试不能随着作者最新粉丝数任意换路。处于 pull 路径的内容仍要完成必要索引，不再逐粉丝入箱。
3. **合并读取。** 同时读取本人收件箱和当前关注作者中需要拉取的内容，按原始 `(create_time DESC, post_id DESC)` 合并、按 post_id 去重，并按当前关系代次和帖子状态过滤。不能为每位作者单独执行一条 SQL。
4. **分页。** 所有来源遵守同一个全局边界；游标绑定读者、模式及版本，避免两路各翻一页再简单拼接。明确补取预算、源数据耗尽与部分来源失败的响应，不把缺一路的结果包装成完整成功。
5. **切换覆盖。** 作者从推变拉、从拉变推时，旧内容不能因最新作者标签改变而消失。一种适合本项目的方案是将分发决定固定在内容级，作者规则只影响后续发布；合并查询保留历史 pull 内容，不仅查询“当前被标记为大 V 的作者”。采用作者级切换水位等其他方案，也必须证明历史与在途任务不漏。
6. **关注与删除。** pull 内容遵守 T02 的关系及删除语义；历史补齐只物化需要入箱的范围，不能把所有高粉作者内容又全量扇出，抵消分流意义。旧收件箱中暂时存在重叠引用时，读取仍需去重。
7. **可恢复与可观测。** Worker 重试沿用已提交策略；记录不同路径的分发量、延迟、候选扫描及合并耗时，指标标签不携带用户或帖子 ID。保留显式 pull 作为对照；显式纯 push 在存在未扇出内容后应标明诊断用途。
8. **默认入口升级。** 先补齐存量路由元数据和关系数据，再切换默认 hybrid。为旧默认 pull 游标给出可执行的兼容窗口或明确刷新协议；不能悄悄按另一种格式解码。

T02 只需保持原始时间排序、关系代次、引用存储、持久化任务与读时过滤这些基础，不提前引入未使用的混合字段或接口。

**5. 后续学习与对照场景**

保留 T01、T02、T02B 的可复跑版本。必要正确性检查随开发进行；用户亲手完成专项造数与压测安排在后期。

| 场景 | 希望观察什么 | 同条件记录什么 |
| --- | --- | --- |
| 多普通作者、频繁读取、稳定发布 | 推模式减少读时聚合的条件与代价 | 读 P50/P95/P99、吞吐、SQL 扫描与执行计划、DB CPU/IO、入箱数量与空间 |
| 少数高粉作者连续发布 | 纯推的写放大、任务排队及对普通作者的影响 | 每帖入箱数、最老任务年龄、投递延迟、DB 写入、Worker 占用 |
| 普通作者与高粉作者混合 | 混合方案是否减少写压力，读合并增加多少成本 | 前述读写指标、两路候选数、去重与补取次数、漏项/重复项核对 |
| 作者双向切换、取关再关注、分发中删除 | 策略和业务生命周期能否同时保持正确 | 输入/提交边界、任务代次、最终可见集合与游标结果 |

报告必须记录硬件与容器限制、数据分布、随机种子、预热、持续时间、并发及读写比例。可以构造高粉和高读场景学习不同方案，但不得把实验构造描述成线上规模，也不预先填写提升百分比。
