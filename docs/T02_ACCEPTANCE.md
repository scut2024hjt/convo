**本地发现与修复**

| 问题 | 实际复现与处理 |
| --- | --- |
| 正常领取误加失败数 | 原 UPDATE 先赋 status=running，后续表达式读到新值。正常领取出现数据库失败数 1、内存 0。状态改为最后赋值，复测两者均为 0 |
| 成功批次未清零内存计数 | 数据库已归零，任务对象仍为 2，下一次错误在上限 3 时直接进入 failed。只在成功提交后同步清零，复测进入 retry；完成、取消、进行中的批次都覆盖 |
| 删除使用错误的详情缓存键 | 实际键有 `:v1` 后缀，删除自行拼接的键没有。使用真实 Set/Get 缓存接口复现旧缓存仍在，改为复用 `postCacheKey` 后清理成功。此前数据库过滤已阻止旧缓存被返回 |
| 测试先关闭连接再清理 | 原用例显示 PASS，但 cleanup 报 database is closed 并留下数据。调整 cleanup 生命周期，清理失败改为测试失败，最终复跑无此错误 |
| T01 手工收件箱样本缺少新归属字段 | 更新旧用例的作者和关系代次，继续覆盖扇出接管、原始时间分页及唯一性 |

此外，将 `convo_bootstrap_follow` 纳入 Docker 镜像；关系任务失败时记录原始错误日志；页面提示移除推拉模式、索引与收件箱清理等实现细节。

**关键正确性证据**

1. 发布先提交与关注先提交用真实 MySQL 锁等待屏障控制，非随机 sleep 推断；两种历史上界及最终集合均正确。
2. fanout 已越过某个低 ID 用户之后，该用户才关注，仍能通过 backfill 获得该帖。未完成旧任务在重新关注后恢复会取消，旧 cleanup 不删除 generation=3 引用。
3. 单任务预算 1 秒，在暂时锁等待解除后正常让出：pending、attempts=1、consecutive_failures=0。持续数据库阻塞也可能阻止让出写入，此时仍依赖租约接管，不承诺数据库不可用时立即保存状态。
4. 真实注册/登录五个账户，先发布四篇历史帖，再由三位读者关注，得到十二条引用。字符串 ID、小页游标、跨用户拒绝、重复操作及代次 1→2→3 均核对；后续新帖正常分发。
5. 投票赞成、重复赞成和撤销仍经过异步链路，MySQL 最终方向/版本为 0:2。
6. 缓存真正命中后本人删除，他人拒绝、本人重复删除仅一个事件。两个清理任务仍 pending 时，详情、各列表、编辑、新投票及两种 Feed 都遵守删除状态；过滤中间 ID 后，剩余票数按 ID 对齐。
7. 保留删除任务后重启，合法待清理索引不误报损坏，清理最终收敛；重放被删帖的原发布任务不复活索引/引用，原票态版本保留。
8. 待删帖仍有索引，同时另一个活跃帖索引缺失，使 MySQL/Redis 总数恰好相同，启动仍以退出码 1 拒绝。恢复样本后正常启动；rebuilding 标记同样拒绝，恢复 ready 后可启动。
9. 最终 API 样本六篇删一篇：MySQL 活跃五篇、Redis 时间/热度索引五篇、三个读者共十二条引用，push/pull 集合与顺序相同。
