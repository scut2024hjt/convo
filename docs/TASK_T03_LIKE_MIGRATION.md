## 2. 目标与成功边界

对外改为点赞/取消点赞两个目标状态。点赞写成功仍表示 Redis 状态与持久化事件已原子产生，MySQL 最终一致；不宣传同步落库、绝对不丢或 exactly-once。相同目标状态重复请求成功，但不增加版本、不改变热度、不生成事件。

本轮不改为 MySQL-first，也不增加 Redis 故障时的 MySQL 直接写入。后者涉及两个写入口和恢复合并，留到后续可靠性任务。读取允许在明确陈旧语义下使用已持久化状态；不能把故障或未知直接解释为“未点赞”。

采用维护窗口迁移，不做滚动混部或在线无停机迁移。新程序必须拒绝旧语义或未完成迁移/重建的状态。升级默认库由用户另行安排，本轮仅在隔离测试资源演练。

## 3. HTTP 与数据契约

所有新增接口沿用 `/api/v1`、现有响应信封、JWT 及业务码风格。ID 和新接口的 version 使用十进制字符串，避免 JavaScript 精度丢失；计数为非负整数。统一校验正 ID、输入长度和上限。

| 接口 | 行为 |
| --- | --- |
| `PUT /post/:id/like` | 设为已点赞；无需目标状态请求体 |
| `DELETE /post/:id/like` | 设为未点赞；重复取消幂等 |
| `GET /post/:id/like` | 读取当前登录用户在该内容上的点赞状态 |
| `POST /posts/like-states` | 请求 `{"post_ids":["..."]}`；去重后最多 50 项，只读当前登录用户状态 |
| 旧 `POST /vote` | 保留旧方向字符串 `"1"` / `"0"` 入口，复用同一业务操作；`"-1"` 明确参数错误 |

新增写接口成功数据至少为 `post_id`、`liked`、`version`、`changed`。可保留内部 direction，不能要求前端继续理解三态。旧 `/vote` 的兼容响应可保留原字段类型，文档说明差异；不要无意改变所有旧调用者。

新增状态读取成功项至少为 `post_id`、`liked`、`version`、`source`、`freshness`。约定：Redis 正常且状态检查通过时 `source=redis, freshness=realtime`；允许的 MySQL 回退为 `source=mysql, freshness=persisted`，可能落后于已接受请求。`realtime` 只表示该次原子读取的当前 Redis 状态，不保证下一瞬间或多端不再变化。

批量结果按 `post_id` 关联，明示不可见/不存在的条目，不能用数组错位或默认 false 代替。整个批次后端不可读可返回统一忙碌；部分内容不可见可返回对应业务状态。不得接受 body 中的任意 user_id 查询他人状态。

删除内容仍按 T02 规则拒绝读取和新写入。发布已经提交但索引任务未完成的写请求仍返回现有索引准备中业务码；状态读取不能将缺失索引/异常类型/未 ready 状态伪装成 Redis 的正常 0。未点赞且无历史记录可为版本 0；取消后的版本墓碑必须保留。

## 4. Redis 写入与本人状态读取

1. 复用现有 Lua 及同一份方向/版本/Stream 数据模型，把新写入限制到 0/1。先做必需类型、就绪状态及内容索引校验；错误时不得部分改热度、方向、版本或 Outbox。
2. 移除七天内才允许投票的限制，历史可见帖子也可点赞/取消。热榜时间窗属于 T05，与用户是否能取消历史点赞分开。保留热度公式基础 `发布时间秒 + 点赞人数 × 432`，T03 不重新设计排序。
3. 对同一用户/帖子的目标状态重复请求，返回当前版本和 changed=false。0→1→0→1 则每次真实变化版本增加一次；并发最终串行化，不要求不同设备用户意图按客户端时间排序。
4. Lua 生成事件改用消息体类型 `like.changed.v1`，字段可复用旧结构。新类型只能携带 0/1。一个真实变化只原子写一个 Stream 事件。
5. 本人状态中的 direction/version 必须取自同一读取边界，例如一个小型只读 Lua；不能两条非原子命令拼出旧方向与新版本。批量最多 50 项，使用 Pipeline/有界批量脚本；MySQL 回退使用一条有界 IN 查询，避免逐条查询。
6. 所有写入口共享已有同一个用户限流窗口，不能新旧路由各给一份额度。版本溢出、Lua 类型错误等必须在可控范围内拒绝，不能静默变回 0。注意 Lua number 的精度边界：若仍用数值比较/返回版本，应明示可精确处理的上限并在迁移/写入前拒绝超界；仅把 JSON 改为字符串不足以修复服务端精度丢失。
7. 个人状态与动态点赞数不进入公开详情缓存。公开 `vote_num` 保留兼容，语义统一为 direction=1 的人数；前端显示“点赞”。不得将负票折算成额外点赞或把净票数当人数。

认证目前依赖 Redis Session，因此 Redis 全部不可用时可能在认证阶段拒绝请求。状态 DAO 的 MySQL 回退不能被描述成整个接口在 Redis 宕机时必然可用。即便读取回退，写请求也不能绕过 Redis/就绪检查直接落 MySQL。

## 5. 旧数据迁移：先定义流程，再提交实现

交付新增顺序迁移文件（预计 `005_like_semantics.sql`）、有界可续跑的维护命令和操作手册；命令名称可自行选择。禁止把一次无条件大表 UPDATE、清空版本或删除重试队列当作迁移。

### 5.1 维护窗口顺序

1. 备份 MySQL、Redis 状态与配置，记录原版本和统计；关闭入口写流量及其他后台写入源。旧 Relay/消费者继续运行，把已接受事件写完。
2. 确认 Stream 长度/待处理、RabbitMQ 主队列 ready+unacked、retry、DLQ 都为 0。查询失败、超时、权限不足、解析失败或非 0 时拒绝继续；不要把无输出当 0。DLQ 必须先人工处理，不能自动清空。
3. 停止所有旧应用/Relay/消费者，避免检查后又有新事件。维护命令再检查积压、所需 schema 和前置版本；使用明确维护确认参数。自动化可检查队列与状态，操作者仍须保证没有旧进程并发写，不能声称仅靠标记阻止已启动旧进程。
4. 执行缺失 schema 迁移，设置持久化迁移状态，开始分批转换。DDL 自动提交，不能宣称整个过程可事务回滚。
5. 转换完成且校验通过后，在同一维护窗口按新语义执行显式 Redis 离线重建。失败则保持不可服务状态，修复后续跑；不得旧 ready 标记复活。
6. 校对版本、点赞人数、活跃内容索引与热度，完成就绪发布后启动新程序，再开放流量。原来的 Redis Session/限流键及无关业务数据不被清空。

排空检查应有真实查询实现、超时和非 0 退出，不只文档里写一句“保证已排空”。可用 RabbitMQ 管理 API 或严格检查返回状态的 `rabbitmqctl`；不要为此换消息组件。运行参数从现有配置/环境读取，不把密钥写入日志、证据包或命令示例。

### 5.2 转换与版本规则

- 旧 direction=1、0 记录方向/版本不变。
- 旧 direction=-1 改为 0，原 version 加 1，保留该用户/帖子的零状态墓碑；不得删除记录、重置版本。例：-1:v7 → 0:v8；重跑仍是 0:v8。
- 转换进度有持久检查点或同等可证明的有界幂等机制，支持进程重启和部分批次成功；更新条件防止一条负票被加两次。迁移统计区分本次/累计，不以重新扫描次数当转换数量。
- `last_event_id` 的处理须明确：保留旧事件来源，另记迁移批次/状态，不伪造已经发布过的新点赞事件。新版本的来源可追溯到迁移操作。
- 非法方向、版本非法/加一溢出、类型不符或统计不一致必须报错并保持未就绪。
- 存量软删除帖的票态也完成归一化与版本保留；重建仍只恢复可见内容的索引，保留 T02 删除保护，不能让历史发布任务复活内容。

### 5.3 语义就绪与恢复

引入持久化的 MySQL 点赞迁移状态和不同于旧 `ready:v1` 的 Redis 语义标记，例如 `ready:likes:v1` / `rebuilding:likes:v1`。新程序启动必须同时验证 schema/迁移已完成和新 Redis 状态。旧二进制再启动会因不识别新标记拒绝；已运行的旧进程仍须由维护步骤停止。

非空旧库即使 MySQL/Redis 总数相等，也不能自动标为新语义 ready。全新数据库的 init.sql 应直接建立新 schema 与已完成的初始迁移状态；空 Redis 的首次初始化只在满足明确的新库/空状态条件时允许。一般的 Redis 数据丢失仍要求显式重建。

重建复用既有命令与批量逻辑，保存每对用户/帖子的版本，包括零状态。热度按点赞人数重算，不能继续用含负票的方向净和。标记发布顺序、转换中断、重建中断和“schema 已改但数据未完成”的重入行为都须写清。T02 已验收的索引成员检查、合法待发布/待删除例外与删除墓碑继续成立。

回滚分两段描述：开放新流量前可以恢复完整备份并配套旧程序；开放新流量后不可简单降级二进制或反向把 0 改回 -1。不要提供会丢弃新接受事件的“一键回滚”。

## 6. 旧消息、新事件与版本隔离

新消息体使用 `like.changed.v1`，旧 `vote.changed.v1` 只用于受限兼容。不能只把旧负票映射为 0 就继续无条件 UPSERT。

迁移完成后，旧类型处理规则：

| 情况 | 处理 |
| --- | --- |
| event_id 已消费 | 幂等 ACK，不再修改状态 |
| 版本低于当前已持久化版本 | 记为 stale 并 ACK，不改变方向/版本 |
| 版本等于当前版本，旧方向归一化后与当前相同 | same_version 并 ACK；旧 -1 的逻辑状态为未点赞 |
| 相同版本但逻辑状态不同 | 冲突，可靠移入 DLQ，保留原因 |
| 旧消息会推进版本，包括当前无该行 | 拒绝推进，可靠隔离到 DLQ，不写业务方向/版本 |

这条隔离防止迁移之后的旧 v9 写进 MySQL，而重建后的 Redis 仍为 v8，使下一次新 v9 与数据库冲突。排空是主保证，旧类型隔离是漏网/重放的保护，不做通用死信回放平台。

新类型只允许 0/1、正版本和有效 ID。保留已有消费去重、单调版本和同版本冲突策略，新消息允许先 v3 后 v2，最终 v3；重复投递不重复累计。校验和拒绝分支不能提前 ACK，DLQ 发布失败仍按现有可靠机制保留原消息。

RabbitMQ 现有队列参数包含固定的旧 retry 死信 routing key。优先保持现有传输 routing key 和队列定义不变，明确区分“消息体业务类型”与“传输路由”；新旧消息共用原管道，消费者按消息体识别语义。若更改路由，必须兼容现有队列参数和 retry 返回主队列的行为，禁止仅替换常量导致 `PRECONDITION_FAILED` 或消息无路由。无需整体重命名 vote 包/队列/指标。

Relay 的 Stream 解码、发布消息体、消费者验证、持久化 DAO 和重建都要覆盖新语义；不能只改 HTTP 和页面。

## 7. 可观测性与前端

复用已有业务日志、HTTP Histogram、Outbox 积压/最老年龄、消费者结果和落库延迟。新路由的指标使用 Gin 模板路径；label 不带 user_id、post_id、event_id。新增 legacy_rejected/like_conflict/read_fallback 等有限结果值时同步面板或查询说明，不做整套监控重构。

日志保留 event_id、post_id、version、实际消费结果及迁移批次等定位字段；不记录 JWT/密码。重复目标状态要能区分 unchanged，保持已有计数逻辑不因新增路由漏统计。维护命令输出转换/校验统计和明确失败步骤。

React 本轮做必要闭环：

- 帖子详情改为点赞/取消点赞，去掉反对票；显示当前点赞人数，保持关注与本人删除交互。
- 进入页面和刷新时读取本人状态；未登录、加载中、读取失败、持久化回退、确认状态分别处理。不能默认未点赞造成闪烁或误操作。
- 同一内容写请求串行化并禁用待处理按钮；网络超时结果未知时重新读取确认，不能直接认为请求失败且未生效。可使用乐观更新，但失败/回读需纠正计数与状态。
- 路由改变/账户切换时清除旧个人状态；迟到响应不能覆盖另一个帖或另一个账户的状态。异步落库回退比本次成功版本旧时，不直接用它覆盖已确认的新状态。
- 页面只展示用户需要的信息，开发实现术语放文档。列表批量本人状态接口作为可复用基础提供，不借此重写整个列表缓存装配；T04/T06 继续负责后续重构。
