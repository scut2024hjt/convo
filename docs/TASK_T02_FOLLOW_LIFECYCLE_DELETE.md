**3. 业务与 API 契约**

沿用 HTTP 200 和 `{code,msg,data}`；原业务码不重编号。对外 ID 仍是十进制字符串，DB 使用 BIGINT，时间统一 UTC。

| 操作 | 需要实现的行为 |
| --- | --- |
| `PUT /api/v1/users/:id/follow` | 首次关注与 inactive→active 重新关注，关系变化和补历史任务在同一 MySQL 事务提交；重复 PUT 不增加关系代次、不重复创建任务、不重置进行中进度 |
| `DELETE /api/v1/users/:id/follow` | active→inactive 与对应清理任务共同提交；重复取关幂等。成功后的新读取立即隐藏该作者，不等待清理 |
| `GET /api/v1/users/:id/follow` | 只返回 active 关系；本人不能关注本人；非法/不存在作者沿用现有错误约定 |
| `GET /api/v1/feed?mode=push` | 原始时间/ID 排序，只返回当前 active 关系相应代次及 `status=1` 的内容；补历史期间允许暂缺，任务完成后覆盖全部约定历史 |
| 默认或 `mode=pull` | 保留现有读取和旧游标契约，更新为 active 关系过滤；继续作为完整数据对照 |
| `DELETE /api/v1/post/:id` | 仅当前 JWT 用户可删除自己的内容；不存在返回现有不存在码，删除他人返回权限错误。同一作者重复删除成功，不重复产生删除事件 |
| 删除后的详情、列表、编辑与新投票 | 删除提交后开始的新请求均遵守不可见/不可修改/不可新投票约定；已开始的读取可能与删除交错，不承诺跨请求快照 |

现有路由定义在 `router/router.go`。保留已有 URL 和响应兼容，不另建一套关注接口。可增加小型、明确的 `syncing`/状态提示，但不要让前端猜测固定几秒后必然完成。

本轮历史规则为：新关注最终可看到该作者截至关注提交边界之前的全部仍活跃历史内容；之后新发布内容由 fanout 覆盖。采用固定边界、有限批次，历史多时允许异步处理较久。不能偷偷改成只补最近 N 条，同时保留旧 pull 全历史却把 push 描述成完整。

重新关注按同样规则补齐，不继承一个已取消任务的进度。取关后遗留引用不得仅因“当前又关注了”就作为新代次已投递结果返回。

**4. 数据模型与关注竞争协议**

实现开始前，在交付说明中写出关系状态、任务状态和两个并发时序。下面是推荐模型，可以采用等价方案，但必须满足同样的不变量。

1. `user_follow` 保留 `(follower_id,followee_id)` 唯一关系，增加 active 状态及不会被删行重置的代次。实际关系变化才推进代次；重复请求不推进。若仍选择物理删除，必须另有持久化代次来源，避免取关再关注恢复成相同 token。
2. `feed_inbox` 增加作者及关系代次，继续只存引用和排序信息。唯一主键不产生重复内容；新代次可更新引用归属，旧代次 UPSERT 不能覆盖较新的代次。读取校验当前 active 关系与匹配代次。
3. 关系补齐/清理采用持久化任务，携带关系身份、目标代次、固定扫描边界、双字段游标、状态、租约 owner、领取 generation、重试与有限错误摘要。关系任务可用独立表，避免伪造带 post_id 的内容发布事件；复用 T01 的有限并发、短事务、代次 fencing 和进度提交方式。
4. 补历史一批的引用写入、关系代次验证和进度提交在同一事务。取关后旧补齐任务应取消或安全结束，不能继续写入；重新关注产生新的任务，旧任务无法倒退新进度。
5. 清理仅处理目标关系旧代次的引用，分批、可重试；旧 cleanup 即使延迟到重新关注之后执行，也不能删掉新代次入箱结果。所有相关写入采用统一锁顺序，处理死锁重试或明确失败，不制造长事务。

必须处理 T01 的特定漏投窗口：fanout 已扫描到 follower_id=500 后，ID=100 的读者才关注。如果历史任务仅记“关注时已有帖子”却没有与并发发布建立覆盖边界，可能两边都漏。时间戳相等、雪花 ID 较大和当前队列为空都不是提交顺序证明。

一种可采用的简单协议是：发布事务和该作者的新关注事务共享同一 MySQL 作者行锁，短暂串行化这两个提交。新关注持有锁时读取已提交历史的固定上界并创建补齐任务；先提交的发布由历史补齐覆盖，先提交的关注由后续发布 fanout 覆盖。该锁不跨 Redis IO，也不覆盖后台整次扫描。要说明 InnoDB 隔离级别和读取视图，确保上界查询不会使用加锁前的旧快照。排序 key 仅用于分页，不当作全局提交序号。采用其他协议也需要同等的覆盖证明与回归检查。

fanout 批次也必须取得并验证当前关系代次。不得读取代次后无条件写入，给取关/重新关注留出旧写覆盖新引用的窗口。重复处理与抢占都保持 `(recipient,post)` 唯一和代次不倒退。

**5. 删除事务、读时过滤与投影收尾**

删除用软删除状态，保留帖子及旧投票记录。锁定帖子检查作者与状态，在同一 MySQL 事务中提交首次状态变更、唯一 `post.deleted` 事件和必要投影任务；重复删除不产生新的事件。HTTP 成功表示这些已持久化，索引和收件箱清理异步完成。

- 详情即使命中 Redis 旧缓存，也不能返回已删除正文。首版可对目标帖子做带超时的 MySQL 可见性校验；DB 无法确认时返回忙碌，不使用缓存猜测可见。不要为少一次查询引入尚未设计完的全量缓存版本体系。
- pull、push、普通列表、分类/排序列表及批量按 ID 读取均过滤 `post.status`。同一检查也覆盖编辑与新投票，避免只在 React 隐藏按钮。
- 删除投影清理详情缓存、全局时间/热度索引、分类索引以及已有分类交集结果等实际读取来源。交集缓存不能全库 KEYS 扫描，给出有限、明确的失效办法；若依靠原有 TTL，仍必须读时过滤并标明空间收敛边界。
- 收件箱清理有按 post_id 扫描的合适索引，按有限批次和持久游标推进。引用残留期间依然不可见；不能一次加载所有收件人或执行无预算大批量删除。
- 旧 publish 索引任务和 fanout 可能尚在运行。仅“执行前查一下 status”不足以防止查完后删除、旧写又落下的竞争。给出可闭合的删除防复活协议，例如原子索引删除标记配合初始化 Lua 拒绝旧写，以及 SQL 写入端的状态/代次校验；不能只取消任务表状态后宣称外部 Redis 写已停止。
- 删除任务、发布任务和启动完整性检查一起调整。重启时合法待删除索引不被误报为全库损坏，真实缺失和 rebuilding 标记仍要拒绝。删除投影不能把其他内容的缺失解释成合法差额。
- 保留原有投票的方向、事件版本及待持久化消息。当前只停止对已删帖接收新投票；已接受的在途事件可以幂等落库，但不能恢复内容可见性或索引。不要在没有排空协议时连同版本 Hash 一并删除。

发布/删除相关事件的 schema、CHECK 约束、领取 SQL、Worker 分支、指标和恢复查询要一起核对。编辑后的完整可靠缓存失效重构留给 T06，已有延迟双删继续保留；本轮删除补偿不可只用进程内 `time.AfterFunc`。

**6. 增量升级、存量补齐与可恢复状态**

新增 `migrations/004_follow_lifecycle_delete.sql` 或等价清晰编号，并同步 `init.sql`。001—003 保持原含义。MySQL DDL 会自动提交，交付前写出备份、前置结构检查、部分执行后的继续方式及回退限制。

已有关注关系初始化为 active 的首个有效代次；原 ID、帖子、投票、版本和历史 Outbox 保留。已有收件箱归属迁移不能造成新旧代次混淆；处理找不到帖子或当前关系的残留条目。

给出显式、可重复执行的存量 bootstrap 入口，用于为迁移前的 active 关系建立历史补齐任务。它应有持久扫描位置、固定或可解释的覆盖上界、唯一任务去重、有限批量与进度查询；重启可继续，不能只依靠“应用启动时扫一次全表”的临时 goroutine。建立任务期间的新关注已由在线事务覆盖。bootstrap 不伪造旧帖的发布事件。

本轮默认仍为 pull；后续默认入口调整另立契约，不作为 T02 验收条件。文档说明何时可认为 push 存量补齐完毕：bootstrap 生产任务结束、对应有效代次任务完成、失败任务可查询，并与相同边界的 pull 结果核对。`done` 的任务计数不能代替可见集合核对。

每个新配置给出默认值、范围校验及 BindEnv；旧配置文件不包含新节时仍可启动。任务主动预算耗尽属于正常让出，不增加失败数，沿用 T01 已修正的行为。新持久任务必须接入 main 的退出/接管流程，禁止无界 goroutine。
